# Перенос рабочей области ASTRA 7 лаборатории в ASTRA 8

Дата: 2026-10-02. ASTRA 8 на коммите `e66f6ba1` (закреплён в установщике); патч совместимости
накладывается и на `astra-src/` (upstream `25c78178`, 2026-10-01). gfortran 13, Ubuntu 24.04 (WSL2).

## Откуда материал

Никита (2026-10-02) прислал архив своей рабочей A7.02 (`a7.tgz`: `MAstraN/`, `EQUIL/`, `user/`, ...),
`EQUIL/SPIDER`, `ASTRA_STRAHL` и мануал STRAHL. Ответы на наши вопросы:

Всё присланное лежит локально в `nikita_input/` (в `.gitignore`). В публичный репозиторий из этого
не попадает ничего: ни исходники A7/SPIDER/STRAHL, ни модели и данные лаборатории. В этом документе

написана им самим: `peizz`, `peic`, `qrcar`, `with`, `qjc`, ...), U-файлы `udb/`.

## 1. Что ломалось и почему

### 1.1. Данные эксперимента

У A8 два читателя exp-файла: Python (`pyparse/exp_parser.py`, при сборке, считает только размер
массивов `nr_x_max` и предупреждения) и Fortran (`src/astra/read_input.f90::read_exp`, при запуске,
читает сами данные). `nr_x_max` из Python задаёт размер `XAXES/DATAX` в Fortran: занизить его
нельзя — проверки границ при `-O0` нет, и запись пойдёт мимо массива.

| что в файлах A7 | Python A8 | Fortran A8 |
|---|---|---|
| `AMJ 2.0d0`, `FACTOR 1.0d3` (фортрановская экспонента) | `float()` падает | читает |
| значение начинается после 17-й колонки: `ZRD13X           0.45d0` | обрезает до `0.45` → падает на `0.45d` | берёт колонки 17–22 = `0.45d`: gfortran такое не читает (`ERROR STOP`), ifort, на котором работала A7, читал |
| комментарий после значения со словом `points`: `NA1  41  ! number of grid points` | — | считает строку заголовком 2D-блока → `Format error in group` |
| строка данных с первой колонки длиннее 20 чисел (`4.79 4.78 …`) | — | `split2array2` пишет 21-е слово за конец массива из 20 → **segfault** |
| старый стандарт `POINTS n` + строки `TEX t v1 … vn` | не учитывает размеры | прибавляет к размеру неинициализированные `nt_u*nx_u` → `Size … cannot exceed 250000` |
| `GRIDTYPE` не указан, текст после чисел (`.2 .3 these are time[s]`), `****`-комментарии | ломают разбор блока | читает |
| одномерный радиальный U-файл (`00000.tes`: только радиус, время — скаляр) | `AttributeError` | **не поддерживается** (`ufheader` требует время первой осью) |

### 1.2. Модели и формулы

| что | в чём дело |
|---|---|
| `CF2 = 0.00457*((AMJ*TIAVB)**0.5)/(ABC*CF1)` | ошибка генератора A8, не A7: `ParseBracket` всегда приклеивает токен перед `(` как имя функции; когда там другая `(`, следующая группа скобок теряет пару → `ValueError` |
| `CC = "work(j,303)"`, `HE = … "work(j,105)"` | в A7 `NEOCL4` писал результаты в `WORK(j,101…304)`; в A8 он пишет в массивы модуля `nclass_mod` (`xe_nc`, `cc_nc`, ...), `WORK` нет |
| `"cc_nc(j)"` в начальных значениях | шаблон `inivar` в `pyparse/const_text.py` не подключал `nclass_mod` (в `detvar`/`postep` подключён) → не компилируется |
| `PEIZZ`, `QRCAR`, `WITH`, `QJC`, ... | формулы из `user/fml` A7 (часть написана Никитой), в A8 их нет; формат A8 — свободная форма, `!`-комментарии, оператор на строку |
| `QOH`, `QETOT`, `WE`, `ITOT`, `PRCAR`, ... | в A8 стали функциями `fnc/<имя>.f90`; одноимённая `fml` перекрыла бы их |
| `SAVE` (`fml/save`) | копирует файлы через `SYSTEMQQ` — функция только Intel-компилятора |
| `equ/log/<модель>` | A8 требует файл параметров на каждую модель (`read_input.f90:98–102`), в A7 его не было |

Соответствие `WORK` → `nclass_mod` сверено по исходникам обеих версий: `MAstraN/sbr/neocl4.f`
(присваивания `work(j,105)`, `work(j,145)`, `work(j,165)`, `work(j,301)`, `work(j,303)`) и
`sbr/nclass_mod.f90` (`xe_nc`, `xp_nc`, `xd_nc`, `jbs_nc`, `cc_nc` — те же выражения). Блоки по 20 на
сорт частиц в одном порядке: `e, i, p, d, t, He3, He4, imp1..3` × `gamma, dn, cn, qcond, x, c, qen,
bs_p, bs_t, polflow`; `301/302/303` → `jbs_nc/jext_nc/cc_nc`. Для `304` (плотность основных ионов)
точного аналога нет.

## 2. Инструмент `astra8-a7to8`

`installer/tools/a7to8.py`, ставится установщиком как `~/.local/bin/astra8-a7to8`.

```bash
astra8-a7to8 <A7>/user ~/astra/a8 NBI_nubeam_Int_CXRS.model --exp DBS_HD_lown0.data
astra8 -m NBI_nubeam_Int_CXRS -v DBS_HD_lown0.data -s 0.15 -e 0.2
```

Что делает:

- модель → `equ/<имя>` (пробелы и `+` → `_`, без `.model`); `"work(j,N)"` → массивы `nclass_mod`;
- формулы, которые модель использует (в коде, не в комментариях), с их `include` → `fml/` в формате A8,
  **только если A8 не знает такого имени** ни как `fml`, ни как функцию `fnc`, ни как переменную;
  `include 'fml/x'`, где `x` в A8 — функция, превращается в вызов `XR(J*HRO)`;
  формула с `SYSTEMQQ` заменяется заглушкой `ИМЯ=0.` с предупреждением;
- симлинки A7 на абсолютные пути (`/home/user/soft/astra/ASTRA_7.02/MAstraN/fml/…`) разрешаются
  относительно распакованного архива;
- `equ/log/<имя>` из шаблона (`flux_feqis`) с `AB, ABC, AWALL, RTOR, BTOR, IPL, AMJ, ZMJ, …` из exp-файла;
  `ABC ≤ AB` (иначе A8 останавливается с `ABC cannot exceed AB`);
- ничего не перезаписывает; печатает, какие формулы A8 оставил свои (`betpl peicl pineu qbrem rlne vdia
  vpsww` отличаются от A7 — сверить вручную).

## 3. Патч совместимости в установщике

Один патч (`install_astra8.sh`, шаг 4) на пять файлов, применяется после `git checkout` выбранной
версии:

| файл | правка |
|---|---|
| `pyparse/exp_parser.py` | U-строки A7 (табуляция, `factor:`); одномерные U-файлы; блоки `POINTS n`; `GRIDTYPE` по умолчанию; числа из строки до первого слова, `!`/`*`-комментарии пропускаются; `d`-экспонента; поле значения расширяется до границы слова (как в Fortran); нераспознанный блок не роняет сборку, но его размер учитывается |
| `src/astra/read_input.f90` | обрезка `! комментариев` после чтения строки; `exp_field`: колонки 9–14/17–22/25–30 расширяются до границы слова; размер прибавляется только для настоящих U-строк |
| `src/astra/parse_utils.f90` | `split2array2` не пишет больше 20 слов |
| `pyparse/parse_as.py` | `ParseBracket` приклеивает предыдущий токен, только если это имя |
| `pyparse/const_text.py` | `use nclass_mod` в `inivar` |

Проверки «ничего не сломали»: вывод Python-парсера для `aug34954`, `AUG33040_2500` — тот же байт
в байт; сгенерированный Fortran для всех 28 моделей `equ/` — тот же (сравнение md5 текста до/после).

## 4. `NBI_nubeam_Int_CXRS` + `DBS_HD_lown0.data`: где остановились

Сборка и запуск проходят; начальные профили физичны (при t=0.15: `q` на краю ≈ 7.7, `MU>0`,
`ELON` 1.19 → 1.69, `TRIA` до 0.28, `AMETR` края 0.233 м). На первом шаге:

```
>>> ERROR >>>  Time =  0.150000 sec
               The rotational transform is less or equal zero at rho_N = 0.928058
```

Полоидальный поток `Fp` на краю становится отрицательным. Что проверено и **не** помогло:
`SGNIP/SGNBT = +1`; `ABC = 0.232` (малый радиус границы `BND`); заданная граница `ITFBE = 1e6`;
начальный ток `CU=CUX` вместо `CU = 1-(RHO/ROC)**0.0001`.

Ловушка, найденная по пути (сама по себе ошибку не устраняет): **`ITFBE` значит разное в A7 и A8**.
В A7 свободная граница включалась только при `ITFBP ≠ 0` и `ITFBE < TIME`
(`MAstraN/.srv/model1.f`, `for/stepon.f:163–166`). В A8 условие одно — `TIME > ITFBE`
(`src/astra/stepup.F90:79`): при `ITFBE = -1` из модели Никиты A8 решает уравнения цепей катушек,
то есть считает со свободной границей, а описания катушек «Глобуса» нет. Для переноса таких моделей
`ITFBE` нужно ставить `1e6`.

Дальше без эталона A7 — гадание. Нужно от Никиты:

1. вывод A7 для этого случая (CDF/скриншот профилей `q`, `CU`, `Fp` на t=0.15 и чуть позже);
2. как задумано начальное условие для тока (`CU = 1-(RHO/ROC)**0.0001` даёт почти нулевой ток);
3. ставил ли он `ITFBP` (в A7 без него `ITFBE` ничего не включал).

Прогон всех exp-файлов на этой модели (шаг t=0.15→0.151, таймаут 40–600 с), 98 файлов:

| итог | файлов | что значит |
|---|---|---|
| чтение прошло, стоп на физике модели | 89 | файл сделан под другую модель: нет нужной величины (`ZEF ≤ 0` без `ZEFX` — 46, `TI ≤ 0` — 37, ...) |
| чтение прошло, стоп `MU ≤ 0` | 7 | как у `DBS_HD_lown0` (§4) |
| чтение прошло, расчёт не уложился в таймаут | 1 | `CXRS_44739_noNeut.data`: процесс крутится на CPU, exp-файл уже закрыт |
| чтение не прошло | 1 | `readme` (§5) |

В 19 файлах есть строки вроде `TN\TN;` (описание графика из модели внутри файла данных): читатель
пишет `unknown key word` и продолжает.

## 5. `readme` + `showdata` (hello world A7) в A8

Не работает, и это не про установку:

- модель `showdata` (`NEQUIL=0;`, `CU:AS; MU=.2*FPR+.185;`) падает в FEQIS даже на родном примере A8
  `aug34954` — это модель A7, в A8 её никто не переносил;
- `exp/readme` — демонстрация всех форматов A7; Fortran-читатель A8 не поддерживает два из них:
  одномерный радиальный U-файл `00000.tes` и блок `POINTS n` + `TE t v1 … vn`.

Для работы лаборатории это неважно: в их 97 рабочих файлах этих форм нет (U-файлы — только в `readme`).
Как «hello world» для A8 оставляем `flux_feqis`/`aug34954` из установщика.

## 6. Попутно: ошибки самого A8

- `ParseBracket` (§1.2) — ошибка генератора, не связанная с A7; стоит отправить мейнтейнерам.
- Сборка с `-fcheck=bounds` падает на родном примере `showdata`/`aug34954`: индекс 51 при размере 50
  (`datax` в `graph_utils.f90`); `reinterp_back` (`numerical_tools.f90:30`) — индекс 0. С обычными
  флагами (`-O0`) это молча проходит.
- `inivar` без `nclass_mod` (§1.2).

## 7. Как воспроизвести

```bash
# A7-архив Никиты распакован в nikita_input/a7 (локально, в .gitignore)
U=~/Work/astra/nikita_input/a7/ASTRA_7.02/user
astra8-a7to8 $U ~/astra/a8 NBI_nubeam_Int_CXRS.model --exp DBS_HD_lown0.data
astra8 -m NBI_nubeam_Int_CXRS -v DBS_HD_lown0.data -s 0.15 -e 0.2 -batch
```

Отладочная сборка (проверка границ массивов): в `platform/env.ubuntu` заменить `FC_FLAGS` на
`-O0 -g -fbacktrace -fcheck=bounds,pointer -w -fPIC -fopenmp -ffree-line-length-none` и удалить
`obj lib mod bin`.
